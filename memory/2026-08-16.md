# 2026-08-16

## Phase II-C hung for 35.5h -- root-caused to the diagnostic probe's second worker pool

Both II-C jobs (39216096 V, 39216098 G, launched Aug 14 22:33/23:40) made ZERO
training steps in 35.5h on 8 A100s. Not slow IO -- a deadlock:

- `py-spy dump` on rank 0: MainThread parked in
  `_try_get_data (dataloader.py:1132)` <- `__next__` <- **`train.py:384`**,
  i.e. `_probe_x, _probe_y_raw = next(iter(loader))`.
- All ~32 dataloader workers in state `I (idle)`, `wchan == 0`, **no `D` state
  anywhere** -- so nobody was blocked in filesystem IO. Rules out the known
  holylfs06 ~27-files/s starvation story.
- Workers still held open ImageNet JPEG fds *opened Aug 15 19:23* -- ~15h after
  job start. So the pool ran, prefetched until its queue filled, and wedged;
  the main process never received batch #0.
- `py-spy dump` on a worker hangs hard enough to drop the ssh connection.

**Mechanism.** `next(iter(loader))` builds a SECOND
`_MultiProcessingDataLoaderIter` -- a full `num_workers` pool per rank (32
processes at 4x8) plus a pin_memory thread -- to fetch ONE batch, then abandons
it. Teardown happens only via refcount `__del__`/`_shutdown_workers`, racing the
epoch loop's own pool on the same mount.

**Fix (invariant, not patch): at most one multiprocess worker pool live per
rank.** Probe batch now comes from a `num_workers=0` DataLoader over the same
dataset and the SAME sampler -- bit-identical images, since
`DistributedSampler.__iter__` is a pure function of (epoch, seed, rank) and
holds no cursor. Global RNG state snapshotted/restored across the fetch so the
construction is provably side-effect-free on the training stream. Cost: one
serial read of `local_batch_size` JPEGs.

Note this line was present in II-A/II-B too and did not fire -- it is a race,
which is exactly why removing the second pool (rather than retrying) is the fix.
