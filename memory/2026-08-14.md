### What is being built
New package `projects/masked-EqM/telemetry/`. Design: **the append-only event log is the
only source of truth; every state document is a fold over it.**

- `schema.py` — typed event envelope `{v, ts, run_uid, exec_id, seq, event}`; EventType
  START/PROGRESS/EVAL/ARTIFACT/NOTICE/OBSERVED/END; RunStatus incl. `LOST`; nonfinite
  values encoded as strings so NaN survives the round trip and stays visible.
- `ids.py` — **content-addressed identity**. `run_uid` = blake2b-64 of the canonicalized
  spec (logical experiment); `exec_id` = `<run_uid>:<job_id>:a<attempt>` (physical
  execution). Requeue reuses the SLURM job id, so job_id alone is not a key — hence the
  attempt counter. `differing_fields()` makes "is this comparison controlled?" computable.
- `emit.py` — one file per exec_id (interleaving becomes unrepresentable), advisory lock,
  tiered fsync (lifecycle events synced, per-step flushed), multi-sink so wandb/stderr/
  jsonl receive the IDENTICAL record.
- `lifecycle.py` — the FSM + **five-layer terminal-record ladder**: normal return →
  exception → signal (raises `Interrupted(BaseException)` so broad `except Exception`
  handlers can't swallow a preemption) → atexit → shell-level seal → reconciler-inferred.
  Plus `heartbeat()` for wedge detection (repo has lost a night to a quota-deadlocked job
  that was indistinguishable from a slow dataloader).
- `read.py` — the scientific gate. **Absolute windows on the PLANNED step axis**, shared
  across arms; `shared_windows()` REFUSES to compare runs planned to different lengths.
  `CompletenessPolicy` is a total predicate with an explicit reason per rejection;
  quarantined runs are returned alongside the good ones so a report can't lie by omission.
  `seq` gaps are positive PROOF of record loss (a timestamp-ordered log can never establish
  this) and quarantine the run even if it has a clean END.

Also built:
- `invariants.py` — **declared invariants as telemetry**, aimed at the bug class that
  already cost this campaign 9 runs. A run declares a property (`frozen_conditioning`,
  `probe_batch`, `data_order`, ...), emits a cheap checksum of it, and the reader verifies
  CONSTANT ones never moved within a run and SHARED ones matched across arms. The
  frozen_label_dropout bug was found by reading code, not telemetry; this makes that class
  mechanically detectable. train.py *asserts* in a comment that RNG state is identical
  across arms — nothing checked it until now.
- `experiments/btm/analyze_image_v2.py` — gated replacement for `analyze_image.py`.
  Absolute shared windows, completeness gate with visible quarantine, per-`kind`
  populations, and a confound check (`controlled_comparison`) that refuses to present a
  headline table when arms differ in more than the manipulated variable. Exits non-zero on
  INVALID/CONFOUNDED so a pipeline can't consume an invalid table.

### Bug found in my own code by the end-to-end test (worth remembering)
First E2E run sealed all three *complete* runs as `timeout`. Cause: `RunRecorder.__exit__`
used `last_step + 1 >= planned_steps`, but `last_step` is the last *logged* step and the
logging cadence is 50, so a run that executed all 2000 steps reports 1950. Fixed properly
rather than by widening the comparison: added `mark_complete()` (the training loop is the
only thing that KNOWS it finished) plus a stride-aware fallback that measures the observed
logging stride instead of hard-coding a tolerance. Lesson: completion is an assertion, not
an inference from a step counter.

### Audit correction (important — my initial audit was wrong here)
The emission audit claimed 14 sbatch files pipe to `tee` without `PIPESTATUS` and therefore
report `COMPLETED 0:0` on a python crash. **False.** All 14 set `set -euo pipefail`, under
which the pipeline's status is the rightmost failing command, so a crash already propagates.
86/92 sbatch set `pipefail`; the 6 that don't use no `tee` at all — the intersection is
empty. Two further corrections from the same agent: `--signal=USR1@120` would have been
INERT without the `B:` prefix (SLURM signals job steps, not the batch shell, and these jobs
run python directly in the batch shell with no `srun`); and a foreground command defers bash
traps until it returns, so a 24h job would process a 120s warning 24h late — the prelude
backgrounds and `wait`s. Signal forwarding by process group also silently delivers nothing
when the shell isn't a session leader.

### Two things found that are worse than the telemetry problem
1. **`scripts/ralph/lock.sh` was not merely racy — it was empirically broken.** 12
   concurrent contenders doing a read-modify-write under it produced a final counter of
   **6/12**. Root cause beyond the known mkdir/pid window: it recorded `$$`, i.e. lock.sh's
   OWN pid, which exits the moment `acquire` returns — so every lock it held read as "dead
   owner" to the next contender. Rewritten around `ln -s` (POSIX `symlink(2)` is an atomic
   test-and-set and the owner record IS the link target, so an ownerless lock is
   unreachable, not merely unlikely). Owner = `$PPID`; staleness uses host+boot_id+pid+
   process start time; foreign-host locks are never probed. 15 tests incl. a **negative
   control** (same protocol without the lock, asserting corruption DOES occur) so the
   passing test can't be vacuous.
2. **`analyze_toy.py` was silently destroying committed results.** The summary key omitted
   `tc` while the group key included it, so the `tc_sweep` section overwrote 6 of 8 rows.
   `btm_vector|K1|eps0.003|ring` reported median 0.00716 (n=7); it is really four groups —

## FID protocol decision (open)

The existing eval_fid.sbatch integrates 250 steps x 0.003 = total time 0.75, a
default tuned for LEGACY EqM. BTM's self-stopping interpolant has Idot_1 = 0, so
the drift vanishes at the data end: **under-integrating truncates transport,
over-integrating is harmless.** Inheriting T=0.75 could silently handicap every
BTM arm at once. Plan: sweep T in {0.75, 1.5, 3.0} on V epoch15 (2k samples,
gpu_test), fix the winner, reuse for every arm. Also note eval_fid.sbatch requires
a SOURCE_ARCHIVE; only the stale sha 3ffaeb5 archive exists, so the BTM FID job
should use the git-clone prelude from btm_image_arm.sbatch instead.

## Two infrastructure bugs that cost 6 wasted job submissions

### 1. `git push origin main` while on branch `btm-fd-scalar` (MINE, load-bearing)

Four commits today reported "pushed" but pushed the STALE LOCAL `main` ref
(7f5de97), not the working branch. The commits never reached the remote.

**Why this is a silent killer specifically on this project:** every cluster job
clones at `GIT_SHA`. An unpushed commit is therefore an UNRUNNABLE job, and the
failure surfaces ~35s in as `fatal: reference is not a tree: <sha>` — a git
error, nothing that says "you forgot to push". The `--depth=50` fetch plus the
`--unshallow` fallback both fail identically, so the retry logic hides it too.

RULE: on this project, submit only after `git ls-remote origin <branch>` shows
the exact sha being passed as GIT_SHA. `git rev-parse HEAD` is NOT sufficient
evidence — it is local-only and says nothing about the remote.

### 2. Apostrophe inside `${VAR:?word}` kills the script at parse time

`OUT_NAME="${OUT_NAME:?... overwrites another arm's FID}"` — bash quote-processes
the word in `${VAR:?word}` EVEN INSIDE DOUBLE QUOTES, so the lone `'` opened a
quote and the script died with `unexpected EOF` before the first command ran.
Symptom: job FAILED in 2 seconds with exit 2:0 and an empty-looking log.
Always `bash -n` an sbatch before submitting; a 2-second FAILED with no output
is a parse error, not a runtime error.
